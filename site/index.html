How it works

Rules first, because most CI failures repeat. A model is the fallback, not the default.

1

Parse

Console output from xcodebuild, or a .xcresult bundle read through xcresulttool, becomes log entries with file, line and column.

2

Classify

Weighted regex rules vote. The strongest match sets the category, the root cause and the suggested fix. Below 60% confidence, --llm asks Claude.

3

Track and report

An actor-based SQLite tracker scores flaky tests over 90 days. Output goes to the terminal, JSON, SARIF, Slack or a GitHub pull request.

Run it

Swift 6 on macOS 14 or later. The first block runs the real tool on the sample log that ships in the repo.

Build from source and triage the sample compile failure

git clone https://github.com/gerardrecinto/xctriage.git
cd xctriage
swift build -c release
.build/release/xctriage analyze \
  Tests/XCTriageKitTests/Fixtures/xcodebuild_compile_failure.log \
  --source xcodebuild

Or use the release binary (arm64 macOS) on your own log

curl -L https://github.com/gerardrecinto/xctriage/releases/latest/download/xctriage-macos.zip -o xctriage.zip
unzip xctriage.zip
./xctriage analyze xcbuild.log --source xcodebuild

Add --llm for the Claude fallback. It needs your own XCTRIAGE_ANTHROPIC_API_KEY; this page never calls it. swift test runs the suite.

What this does not do
  • The Swift tool cannot run in a browser. This page re-runs its rule table and a port of the log line filter, not the full parser, the xcresult reader, the tracker or the LLM path.
  • Confidence is the winning rule's weight, not a calibrated probability.
  • A log no rule matches comes back as unknown with 0% confidence, which is when the optional LLM fallback applies.
